# AI Job Desk — the web front end

The markdown report is fine to read once. It cannot hold a decision: which roles
you already looked at, which you applied to, what you thought. This site does.

```
src/main.py  ──>  web/public/data/jobs-<date>.json   ranked run, static
                  web/public/data/index.json         day index
                        │
                  web/public/index.html              the page
                        │
                  web/api/notes.js  ──>  Postgres    your status + notes
```

Job data is **static JSON** regenerated by each pipeline run. Notes live in a
database so they survive the next run, the next deploy and a different device.

---

## Deploy

One-time:

```bash
cd web
npm install
npx vercel login        # opens a browser; this is the step only you can do
npx vercel link         # choose the "mukul1312's projects" scope
```

Then, after every pipeline run:

```bash
cd web && npx vercel --prod
```

That is the whole loop: run the pipeline, deploy, open the site.

> Vercel's MCP connection and the `vercel` CLI authenticate separately, which is
> why the login above cannot be done for you from a non-interactive session.

## Notes storage

The site works with **no database at all** — notes fall back to browser storage
and the footer says so. That means it deploys and is useful before any setup.

To sync notes across devices, add a Postgres store. Your personal Vercel team
already has the **Supabase** marketplace integration on the Free Plan (500 MB,
no payment method needed):

**Vercel dashboard → Storage → Create → Supabase → connect to `ai-job-desk`**

Vercel injects the connection string automatically. The handler accepts
`DATABASE_URL`, `POSTGRES_URL`, `POSTGRES_PRISMA_URL`,
`SUPABASE_POSTGRES_URL` or `POSTGRES_URL_NON_POOLING`, whichever the provider
sets, so nothing needs configuring by hand. To point it somewhere else instead:

```bash
npx vercel env add DATABASE_URL production
```

The driver is postgres.js, not a vendor SDK, so Supabase, Neon or any other
Postgres all work without a code change.

> Keep this on a **personal** account. These rows say which jobs you applied to;
> they do not belong on an employer's infrastructure.

The table is created on first write:

```sql
CREATE TABLE job_notes (
  job_id     text PRIMARY KEY,   -- stable hash of the job URL
  status     text NOT NULL DEFAULT 'none',
  note       text NOT NULL DEFAULT '',
  title      text, company text, url text,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

`job_id` is a hash of the listing URL computed identically in the browser and
stored here, so a note written three weeks ago still attaches to the same role
when it reappears in a later run — and survives even after that day's JSON is
pruned.

### Locking it down

Preview and production URLs are guessable. If the link is ever shared, set a
shared secret and the API refuses writes without it:

```bash
npx vercel env add NOTES_TOKEN production
```

Without `NOTES_TOKEN` anyone with the URL can read and write notes. For a
private deployment that is usually fine; decide deliberately.

## What the page gives you

| | |
|---|---|
| **Day selector** | every run that has been deployed, newest first |
| **Summary strip** | ranked · new today · India-hireable · best overlap · top region · needs JD |
| **Filters** | search, New, India-hireable, include unscored, by your own status |
| **Per job** | fit score, overlap hours, salary in LPA, India evidence, which resume to send |
| **Per job, yours** | status (Untriaged → Shortlist → Applied → Interview → Pass) and free-text notes |

Unscored roles are hidden by default and reachable with **Include unscored** —
they cleared the timezone and salary filters but had no description to grade.
Most of the Indian supply lands there, because gethired's public API does not
publish descriptions.

Notes save as you type, debounced, one write per job.
